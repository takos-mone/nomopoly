## 1. 土台となるアーキテクチャ決定

| 項目 | 決定 |
| --- | --- |
| 対戦形態 | 同一端末パス&プレイ(オンライン対戦は後回し) |
| 技術スタック | Web(React等)+ブラウザ。インストール不要で配布・修正が速い |
| 資産軸 | **飲酒量のみの単一軸**。モノポリーの「お金」は廃止し、土地購入・店舗建設もすべて飲酒量(unit)で管理 |
| 酔いゲージ・脱落システム | **導入しない**。累計飲酒量はスコア・演出用の記録に留め、実飲酒の強制や脱落判定はアプリ側で行わない(安全面・法的リスク回避) |
| 勝利条件・終了条件 | モノポリー式。資産(土地・店舗)を使い切った、または一定unit到達で脱落するプレイヤーが出て、最後に残った1人が勝者 |

## 2. 飲酒量(unit)システム

- **単位はml換算しない。「1 unit」の実量は、遊ぶ飲み会ごとにプレイヤー側が事前に決める**(例:1 unit = 一口、1 unit = 5ml、ノンアル可、等)。アプリ内はすべて無次元の unit で計算する。
- 1イベント・1ターンあたりの unit 上限は**設けない**(倍率重ねも同様に上限なし)。ゲームバランスは今後の実プレイテストで調整する。
- 倍率カード(倍プッシュ・大盤振る舞い等)の重ねがけにも上限を設けない。理論上無限に乗算されうる仕様として実装する。
- 起動時または初回プレイ時に、「unit の実量は各自で決めてください、無理なく・ノンアルコールも可」という注意文を表示する(実装はMVP範囲内、詳細UIは未設計)。

## 3. 資産・価格スケール

- 土地・店舗の価格体系は **1〜50 unit 程度の小数値スケール**。モノポリーの $60〜$400 のレンジを比例縮小して割り当てる。
- 店舗レベルの飲酒量(原案3.3のml表)も同様に unit 換算で再定義する(実際の数値表は今後の実装作業で確定)。

## 4. 盤面・特殊マス

- 盤面規模: **モノポリー準拠40マス**。既知のバランスを流用する。
- GO / 刑務所 / 鉄道・電力会社に相当する特殊マスは、**飲み会テーマに全て置き換えて模写**する(世界観の統一を優先)。
  - 例(後日詳細化): GO→乾杯ポイント取得、刑務所→一気飲み待機/一歩道量、鉄道・電力会社→コンビニ・タクシー等のユーティリティ系店舗
  - 具体的なマス割り当てとカード文言は未確定 → 実装フェーズで詳細設計する

## 5. カードシステム

- チャンスカード・共同基金カードは**各16枚(合計32枚)**。モノポリー実物の枚数に準拠し、カテゴリごとに数枚ずつ配分してMVPで実装、後から拡張する。
- 出現確率は**シンプル均等確率**。山札から直接ランダムに引き、使用後はシャッフルして戻す(モノポリー方式)。
- カードは**即時使用・手札なし**。引いたカードはその場で効果を発動して捨て札へ。手札管理UIは実装しない。
- カード効果の重複ルール・倍率重複ルールの詳細(コンボの具体的な処理順序など)は**未確定**。「コンボを許容する」方針のみ確定しており、詳細な演算順序は実装時に個別設計する。

## 6. プレイヤー間要素(MVPスコープ)

- MVPで実装するのは**指名システムのみ**(「あの人に一杯」等、原案5章のカード群)。
- 投票システム・交渉システム・土地交換・飲酒量の譲渡・同盟協力要素は**MVP後回し**。データモデル上は将来追加しやすい形にしておく。

## 7. 人数・時間

- プレイヤー人数: 2〜6人
- 1セッション想定時間: 30〜60分

## 進行体験の改善(2026-08-20 ユーザー要望まとめ)

### 通知キューへの一本化(設計判断)
着地説明・カード効果説明・獲得通知・強制移動演出はいずれも「タップで送る全画面通知」であり、
個別のポップアップとして実装すると表示順が破綻する(例: 家賃確認がカード説明より先に出る)。
そこで `GameState.notices: Notice[]` という**単一のキュー**に統一し、先頭から1件ずつ表示、
`DISMISS_NOTICE` で消化する方式にした。通知が残っている間は ROLL_DICE / END_TURN と
家賃・指名モーダルをすべて抑止するため、順序が保証される。

- **マスの説明**: `logic/squareInfo.ts` の `describeSquare()` が、所有状況(未所有/自分/他人/抵当)に応じて
  1〜2行の説明を返す。着地するたびに `landing` 通知として表示。
- **カード効果の説明画面**: 引いたカード名と効果説明を `card` 通知として表示。効果適用より先にキューへ積むため、
  「カードの内容 → その結果(獲得など)」の順で見える。
- **獲得通知**: 免除権(GO周回/カード/コイントス/抵当)、土地取得、無料改装で `gain` 通知を出す。
- **カード増量**: チャンス・共同基金とも16枚→24枚(合計48枚)。既存の効果種別の組み合わせで追加し、
  カード効果エンジンには手を入れていない。
- **サイコロの停止確認**: `ROLL_DICE` に任意の `dice` を渡せるようにし、UI側で先に出目を確定・表示してから
  「Nマス進む」のタップで初めてディスパッチする。出目を見てから盤面が動く。
- **手番プレイヤーの駒を強調**: 金色のリング+パルスアニメーション(`.board-square__token--current`)。
- **GOマス**: 「一軒目(乾杯)」→「GO」に改称。免除権は**1周につき+2 unit**に統一(通過・ちょうど到達とも同額)。
  従来は通過+3/到達+5だった。
- **終電を逃したマス**: 着地時点では駒を動かさず、`transport` 通知を閉じた瞬間に
  タクシー待機所へ**ワープ**させる(`useTokenAnimation` の `snapPlayerIds`)。
  1マスずつホップさせると「歩いて向かった」ように見えてしまうため。
- **所有者表示**: 色の下線ではなく、マス左上に**所有者の絵文字マーク**を出す方式に変更。
  マーク分はマス名の1行目を `text-indent` で字下げして重なりを回避。
- セーブ形式は v2 に更新(GameState構造の変更に伴い、v1のセーブは読み捨てる)。

検証: 実機幅(375px)とデスクトップ幅の両方で通知表示を確認。強制移動は駒がワープすること(120ms以内に到達、
ホップなら20マス×280ms=5.6秒)を実測。通知順序が landing → card → gain になること、GO周回が+2ちょうどであること、
デッキが24枚ずつであることをモジュール直接呼び出しで検証。4ターン通し実行でコンソールエラーなし。

**症状**: 操作していないのに効果音が鳴り出す。

**調査**: `OscillatorNode.prototype.start` を差し替えて発火元のスタックを記録し再現を試みた。
完全放置(6秒間、無操作)では発火0件。一方、**カードを引いていないターンで駒の移動が完了した瞬間**に
`playCardDraw()` が発火することを確認した。タップから1〜2秒遅れて鳴るため、体感としては
「放っておいたら勝手に鳴った」になる。

**原因**: `App.tsx` が `cardDraw={isAnimating ? null : state.lastCardDraw}` を渡している。
`state.lastCardDraw` はカードを引いた後もゲーム状態に残り続けるため、駒が動くたびに
`isAnimating` が true→false と切り替わり、propが `null` →「同じ古いオブジェクト」に戻る。
`CardDrawOverlay` の `useEffect(..., [cardDraw])` はこの参照変化で再発火し、
**過去に引いたカードの音と演出を鳴らし直していた**(一度でもカードを引くと、以降すべての移動で再発)。

**修正**: `CardDrawOverlay` に「どのseqまで再生済みか」を保持する ref を持たせ、
同じ `seq` では再生しないようにした。ドローごとに `seq` は加算されるため、正規のドローは従来どおり鳴る。

**検証**: 修正後、カードを引かないターン3回でサイコロ音のみ(`playCardDraw` の混入なし)を確認。
ドローごとに `seq` が 1→2 と更新されることをモジュール直接呼び出しで確認。

### 同時に対応した表記・UI変更
- 「小休憩スポット」→「**喫煙所**」、「GO」→「**GO (自宅)**」に改称。
- **脱落ラインの設定を「詳細設定」の中から主要項目へ昇格**。折りたたみの中にあり気づかれていなかった。
  あわせて入力を数値stateから文字列stateに変更した。従来は `Math.max(10, ...)` で入力途中の値が
  即座に丸められ、"50" と打とうとして "5" の時点で 10 に化けるため打ちにくかった。
  空欄・0・不正値はデフォルト(80 unit)にフォールバックし、「今回は N unit で始まります」と常時表示する。

## 次のアクション候補(2026-08-20 さらに続き4) — ルールエンジンのエッジケース監査

明示的な要望が尽きたため、reducer・脱落処理・カード効果を体系的に監査し、実バグを2件修正した。

- **脱落プレイヤーが指名対象から除外されていなかった(安全性に関わる不具合)**: 脱落者を除外していたのは`TargetChoiceModal`だけで、カードのランダム/左隣/最富/最貧指名、デュエルのランダム相手、`allDrink`/`allExemption`、`reduceRichestDrinkTotal`、交渉の譲渡先(`DrinkResolutionModal`)はいずれも脱落者を含んでいた。脱落ラインは「これ以上飲ませない」ための仕組みなので、脱落後も飲まされるのは設計意図に反する。全経路で生存者のみを対象にするよう修正(`livingOthers`)。
  - `richest`/`poorest`はカード文面が「最も所有物件が多い/少ないプレイヤー」で自分自身も対象になりうるため、**自分を含む生存者全員**から選ぶ(他の指名系と範囲が異なる点に注意)。
  - 生存する対象が存在しない場合は例外を投げず「対象になるプレイヤーがおらず不発」とログして無効化する(`noTargetState`)。
- **`RESOLVE_DEFERRED`が別人の先送り分を消化していた**: アクションが`index`しか持たず、reducerが`players.find(p => p.deferredDrinks.length > index)`で「先送り分を持つ最初のプレイヤー」を拾っていた。P0が[5]、P2が[10,4]を持つ状態でP2の詳細から「今飲む」を押すとP0の5 unitが消える。アクションに`playerId`を追加し、範囲外indexと不明なplayerIdは無視するようにした。

検証(Vite経由で実モジュールを直接呼び出し):
- 脱落者2名を含む4人構成で各指名系を300回試行し、脱落者が一度も選ばれないことを確認。
- 誰も脱落していない通常構成での回帰確認(random→他3人 / leftNeighbor→左隣 / richest→最多所有 / poorest→最少所有 / currentPlayer→自分)。挙動不変。
- 生存する他プレイヤーが0人の状態で drink(random)/drink(leftNeighbor)/duel が例外を投げず不発ログになることを確認。
- `RESOLVE_DEFERRED`が指定プレイヤーの指定indexのみを消化し、他プレイヤーの先送り分が残ることを確認。
